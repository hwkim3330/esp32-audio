# 게임보이 + 전자종이 한 장

ESP32 가 롬을 플래시에 들고 에뮬레이터를 돌리고, 결과를 벽에 붙은 전자종이 태그 한 장에
그린다. PC 도 화면도 없다.

```
Sketch uses 2,235,939 bytes (71%)   ← 롬 1MB 포함, 여유 약 890KB
런타임 내부 DRAM 여유 47KB (전송 중 41KB)  ← 가장 빠듯한 자원
```

## 롬은 이 저장소에 없다

`tools/gb_eink/embed_rom.py` 가 로컬 롬 파일에서 `rom_data.h` 를 만들고, 그 헤더는
gitignore 된다. 상용 롬을 공개 저장소에 올리는 것은 배포다 — `pokedex` 쪽에 세운
BYOR 방식과 같다. 저장소에는 만드는 도구만 있다.

```bash
python3 tools/gb_eink/embed_rom.py ~/Downloads/"Pokemon - Red Version (K).gb"
arduino-cli compile --fqbn \
  'esp32:esp32:esp32:PSRAM=enabled,FlashSize=4M,PartitionScheme=huge_app,CPUFreq=240' \
  firmware/gb_eink
```

한글판 Red 는 `cart 0x1B = MBC5+RAM+BAT`, 롬 1MB, 세이브램 32KB 다(일본·미국판 Red 는
MBC3). peanut-gb(MIT, deltabeard) 가 둘 다 지원한다.

## 실측 — 굽고 재서 얻은 숫자

| | 처음 | 지금 |
|---|---|---|
| 갱신 1회 | 11,326ms | **2,014~8,617ms** |
| 그중 전송 | 9,005ms (592파트) | **673ms (20파트)** |
| 패널 통보 | 30ms | 28ms |
| 게임 | 13.6초 프리즈 | **안 멈춤** (전송을 코어 0 으로) |
| 프레임률 | 75fps (25% 빠름) | 53.9fps (목표 59.73) |

구간 계측이 통념을 뒤집었다. **패널 리프레시는 시간 비용이 아니다**(28~30ms). 시간은 전부
BLE 연결이고, 그것은 태그가 리프레시 후 잠들어 광고를 늦게 하는 시간이다. 그래서 두 장을
번갈아 쓴다 — 한 장을 굽는 동안 다른 장이 깨어나므로 그 대기가 일하는 시간이 된다
(실측: 같은 회차에서 방금 쉰 :81 은 연결 698ms, 직전에 구운 :78 은 7,300ms).

### 파트는 줄일 수 없다 — 네 가지를 시도했다

| 시도 | 결과 |
|---|---|
| 파트 크기 키우기 | 태그가 244(데이터 240B)로 고정. **MTU 517 을 요청해도 244** |
| 페이로드 압축 | 모델 표에서 이 태그(296×128)는 `compression=false` — 없는 기능 |
| 연결 간격 7.5ms 요청 | **태그가 무시.** 파트당 33.6ms 불변 |
| 폴링 간격 5ms → 1ms | 불변 — 라디오 쪽이 범인이라는 증거 |

파트당 33.6ms 가 파트 수·평면 수와 무관하게 일정하다. 태그가 정하는 연결 간격이고
우리가 당길 수 없다. **그래서 남은 유일한 레버가 바이트를 줄이는 것**이다.

### 적색은 보내지 않는다 (짝비교)

같은 굽기에서 갱신마다 번갈아 보내 태그 상태·거리·배터리를 같게 맞춘 뒤 비교했다.

| | 페이로드 | 파트 | 전송 |
|---|---|---|---|
| 흑백만 | 4736B | 20 | **673ms** |
| 흑백+적 | 9472B | 40 | **1273ms** |

정확히 두 배다. 우리는 적색을 화면에 쓰지 않으므로 뺀다(`AB_RED 0`). 깜박임 차이는
**우리 계측으로는 알 수 없다** — 태그가 완료를 통보한 뒤에 자기 패널을 굽기 때문에
`패널 28ms` 는 통보까지의 시간이고 굽는 시간이 아니다. 눈으로 판정할 몫이다.

전제 하나: 지금까지 적색 평면을 흰색으로 채워 보냈으므로 적색 레이어가 깨끗하다.
전자종이는 잔류형이라 더러운 상태에서 적색 전송을 끊으면 그 적색이 영구히 남는다.

## 계측이 반박한 내 추측 셋

기록으로 남긴다. 굽기 전에는 셋 다 그럴듯했고 셋 다 틀렸다.

**1. "패널 웨이브폼이 병목이라 못 줄인다."** 틀렸다 — 패널 통보는 28~30ms 다. 깜박임이
눈에 크게 보여서 시간도 클 것이라 여겼는데, 태그는 완료를 통보한 뒤에 자기 패널을 굽는다.
깜박임과 소요 시간은 **다른 문제**였고, 섞어서 "느리다" 로 뭉치는 동안 고칠 수 있는 것을
못 고쳤다.

**2. "연결을 붙들면(keep_open) 1.5초를 아낀다."** 무력했다 — 태그가 자기 쪽에서 링크를
끊는다(배터리 기기다). 전송마다 `[특성]`·`[CCCD]`·`[협상]` 이 다시 찍히는 것이 증거다.
`keep_open` 은 코드에 남아 있지만 이 태그에서는 효과가 없다.

**3. "파트를 줄이거나 연결 간격을 당길 수 있다."** 넷 다 막혔다(위 표). 파트당 33.6ms 는
태그가 정하는 값이다.

실제로 효과가 있었던 것은 **두 장 교대**(연결 대기를 일하는 시간으로 바꾼다), **적색 제거**
(바이트 절반), **파트 재협상**(592파트 → 20파트), **전송을 다른 코어로**(프리즈 제거)였다.
`CMD 0x02` 의 마지막 세 바이트는 여전히 용도 미확인이고, 거기에 모드 플래그가 있을
가능성만 남아 있다 — 스윕해 보지 않았으므로 단정하지 않는다.

## 프레임을 보내지 않는다 — 장면이 바뀔 때만

갱신 하한 8초 + 실제로 태그에 나갈 픽셀이 12% 이상 바뀔 때만 보낸다. 게임 프레임을
비교하면 의미가 없다 — 합성된 1비트 평면을 XOR 해서 센다. 하한을 먼저 보므로 하한을
안 넘겼으면 합성 비용조차 쓰지 않는다.

## 잔상은 우리가 그린다

8초에 한 장이면 그 사이의 움직임이 전부 버려진다. 그래서 어두운 픽셀이 지나간 자리를
누적해 두고(`TRAIL_DECAY`) 보낼 때 함께 그린다. 장노출 사진과 같은 원리다 — 한 장에
여러 순간이 겹쳐서 **어디를 지나왔는지가 보인다.** 패널의 물리적 잔상에 기대는 것이
아니라 비트맵 안에 있으므로 재현 가능하고 조절 가능하다(`TRAIL_DECAY 0` = 영구 궤적).

1비트로 내릴 때는 **4×4 베이어 순서 디더**를 쓴다. 오차확산은 프레임마다 무늬가 흔들려서
전자종이에서 지지직거린다 — 정지 화면에는 순서 디더가 맞다.

레이아웃: 160×144 를 최근접으로 142×128 로 줄여 왼쪽에, 남는 154×128 을 상태판으로
쓴다(프레임 수, 갱신 횟수, 태그 전압, 키 안내). 1비트 화면에서 보간은 격자무늬만 만든다.

## 버튼 6개로 게임보이 8개

**START·SELECT 를 길게 누르기로 겹치면 안 된다.** A/B 는 가장 많이 쓰는 키이고 누르고
있어야 하는 경우도 있는데(달리기, 연타), 그때마다 START 가 튀어나간다. 그래서 **동시
누르기**로 낸다 — 코드는 단발 입력을 방해하지 않는다.

| | |
|---|---|
| K1 K2 K3 K4 | 위 아래 왼 오 |
| K5 / K6 | **A** / **B** |
| K5+K6 | START |
| K3+K4 | SELECT (왼+오는 게임에서 같이 눌릴 일이 없다) |
| K1+K2 | 강제 갱신 (위+아래도 같이 눌릴 일이 없다) |

코드가 성립하면 그 두 키의 단발 입력은 내지 않는다 — 안 그러면 START 를 누를 때 A 와
B 가 같이 들어간다.

## 메모리 배치

프레임 버퍼와 궤적은 **내부 DRAM** 에 둔다(각 23KB). 처음에 둘 다 PSRAM 에 뒀는데 그게
가장 뜨거운 경로다 — `draw_line` 이 스캔라인마다 쓰고 `trail_accum` 이 프레임마다 23K
픽셀을 읽고 쓴다(60fps 면 2.7MB/s). PSRAM 은 내부 SRAM 보다 한참 느려서 에뮬 속도를
그대로 깎는다. 세이브램(32KB)만 PSRAM 으로 보낸다 — 접근이 드물다.

롬은 플래시에서 `pgm_read_byte` 로 읽는다. 1MB 를 RAM 에 올릴 방법은 없다.

## 굽고 확인한 것 / 남은 결함

확인됨: 에뮬이 실기에서 돈다(POKEMON RED 부팅, 프레임 진행), 롬이 플래시에서 읽힌다,
태그 두 장 교대 갱신, 전송 중에도 게임이 멈추지 않는다, 파트 재협상, 적색 제거.

남은 결함:

- **프레임률 53.9fps** (목표 59.73). `vTaskDelay(1)` 의 1ms 틱 해상도로 보인다. 페이싱이
  없을 때는 75fps 로 25% 빨랐다 — 그건 성능이 좋은 것이 아니라 게임이 틀리게 도는 것이다.
- **GPIO36 은 내부 풀업이 없다.** 부팅 로그에
  `gpio_pullup_en: input-only pad has no internal PU` 가 찍힌다. K1(위)이 외부 풀업에
  의존하는데 보드에 있는지 확인하지 않았다.
- **`:78` 이 스캔에서 빠지는 일이 있다**(전압은 2.80V 로 정상). 그 회차는 한 장으로 돈다.
- **8초 하한에서 플레이가 되는가는 사람이 판정할 몫이다.** 오버월드 이동은 답답하고
  배틀·대화처럼 턴제인 구간이 이 매체에 맞는다. 강제 갱신(K1+K2)을 넣어둔 이유다.
- `esl_bwr.cpp` 를 `radar_display` 에서 복사해 왔다(아두이노는 스케치 폴더 안의 파일만
  컴파일한다 — `cn_infer.c` 가 네 스케치에 복사돼 있는 것과 같은 이유다). `keep_open` 과
  파트 재협상은 이쪽 사본에만 들어가 있다.
