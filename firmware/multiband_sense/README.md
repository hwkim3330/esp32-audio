# 멀티밴드 2.4GHz 센싱 — 라디오를 전부 센서로

이 칩의 2.4GHz 라디오를 동시에 돌려 대역을 넓게 본다.

## 왜 대역을 넓게 봐야 하는가

멀티패스 페이딩은 **주파수마다 다르다.** 어떤 주파수에서는 사람이 지나가도 신호가
거의 안 변하는데(널 지점), 다른 주파수에서는 크게 변한다. 대역을 넓게 보면 환경을
독립적으로 여러 번 보는 셈이고, 그게 주파수 다이버시티다.

| 라디오 | 주파수 | 얻는 것 |
| --- | --- | --- |
| WiFi CSI | ch1/6/11 = 2412/2437/2462 MHz | 20MHz 창, **서브캐리어 64개** (가장 세밀) |
| BLE 광고 스캔 | ch37/38/39 = 2402/2426/**2480** MHz | **대역 양끝**, RSSI 만 |
| BT Classic | 79채널 호핑 | **쓰지 않음** (아래) |

WiFi CSI 만 쓰면 2412~2472 창 하나다. BLE 광고 채널을 더하면 **2402·2480 — 양끝**이
들어온다.

**BT Classic 은 뺐다.** inquiry 가 12초씩 걸려 감지 주기가 무너지고, WiFi 와 프런트엔드를
다투어 CSI 프레임률을 떨어뜨린다. BLE 스캔은 훨씬 가볍고 대역 양끝을 이미 커버하므로
비용 대비 이득이 없다.

**오디오(HFP/A2DP)와는 동시에 못 한다.** 라디오 프런트엔드가 하나라서 오디오 스트리밍은
BT 를 독점해야 하고 센싱은 계속 호핑해야 한다. 여기서는 센싱을 택했다.

## 실기 결과

```
[wifi] CSI 활성화
[ble] 수동 스캔 시작 (광고 채널 37/38/39)

ch2412:1.0 2437:0.9 2462:1.7  | BLE 5/39 흔들림 (유효39, 9878광고) 점수1.3  | 대역 1.7  sc64 준비3/3
```

64초에 BLE 광고 **9,878건 = 초당 154건**, 기기 39개. WiFi CSI 는 3채널 모두 기준선 완료,
서브캐리어 64개. 빌드 1.6MB(51%), DRAM 19%.

빈 방에서 대역점수가 **1.2~2.1** 로 임계값 3.0 아래에 안정적으로 머문다.

## 통계 결함을 실측으로 잡았다

처음엔 BLE 점수를 **기기별 z-score 최댓값**으로 뒀다. 그러자 **아무도 안 움직이는데
점수가 계속 3.1** 을 찍었다.

**다중비교 문제다.** 노이즈가 있는 48개 변수의 최댓값은 우연히 3σ 를 넘는 게 정상이다.
기기가 많을수록 오탐이 늘어난다.

고친 방식이 물리를 반영한다 — **사람이 지나가면 여러 링크가 동시에 흔들리고, 노이즈는
하나씩 튄다.** 그래서 최댓값 대신 **2σ 를 넘는 기기의 비율**을 쓴다. 빈 방에서 5/39
(13%) 수준이고, 사람이 지나가면 이 비율이 올라가야 한다.

WiFi 쪽도 고쳤다. 기준선 프레임을 채널당 60 → 40 으로, 채널 체류를 3초 → 6초로 바꿨다.
채널을 순환하는데 프레임 수가 크면 학습이 안 끝난다(실측: 50초에 3채널 중 1개만 준비).

## 대역 점수는 최댓값을 쓴다 — BLE 와 반대다

WiFi 채널들 사이에서는 **최댓값**이 맞다. 널 지점 때문이다 — 어떤 주파수에서 신호가
안 변해도 다른 주파수에서 변하면 사람이 있는 것이다. 평균을 쓰면 그게 희석된다.

BLE 에서는 최댓값이 틀렸고 WiFi 채널 간에는 최댓값이 맞다. 차이는 **독립 관측의 수**다.
WiFi 는 3개(널을 피하려는 목적), BLE 는 39개(우연한 극단값이 보장되는 수).

## 버튼 6개 — 스스로 검증하기 위한 계측기

이 스케치의 가장 큰 구멍은 "빈 방 기준선만 있고 사람이 지나갈 때를 모른다" 였다.
그런데 나는 보드 앞에 없다. 그래서 **보드가 스스로 대조군을 모으게** 만들었다.

| 키 | 짧게 | 길게(2초) |
|----|------|-----------|
| K1 | 마크 토글 (지금부터의 창을 "움직임 있음"으로 표시) | 기준선 재학습 |
| K2 | 임계 −0.5 | |
| K3 | 임계 +0.5 | |
| K4 | 채널 고정/순환 전환 | |
| K5 | BLE 통계 초기화 | 통계 출력 |
| K6 | 통계 출력 | |

K1 로 표시한 창과 안 한 창의 점수 분포를 따로 누적해서 `print_stats()` 가
평균·적중률과 **Cohen's d** 를 낸다. d 가 0.8 을 넘으면 "센서가 사람을 본다" 를
숫자로 말할 수 있다. 사람이 필요하긴 하지만, 필요한 건 **버튼 한 번**이지
관찰자가 아니다.

K6(GPIO13)은 부팅 스캔에서 LOW 로 읽히면 자동 비활성된다(GPIO22 와 간섭한다).
그래서 통계 출력은 K5 길게로도 되게 이중화했다.

## LED — 핀을 못 찾았으므로 후보를 전부 몬다

이 보드의 LED 핀은 끝내 확정하지 못했다(D4/D5 가 켜지는 건 봤지만 어느 GPIO 인지
모른다). 그래서 후보 4개 **{22, 21, 2, 4}** 를 전부 같은 패턴으로 구동한다.
GPIO22 는 PA_ENABLE 과 겹치는데, 앰프가 어차피 안 울리므로 여기서는 문제가 없다.

**GPIO16 은 절대 건드리지 않는다** — PSRAM 이다. 출력으로 토글하면 즉시 재부팅 루프.

패턴: 느린 숨쉬기 = 대기, 빠른 깜빡임 = 대역점수 임계 초과, 두 번 깜빡 = 마크 중.

## 용량 — 무엇이 어디에 있는가

```
플래시  1,707,659 / 3,145,728  (54%)   huge_app 파티션
내부DRAM   65,664 /   327,680  (20%)   전역
```

내부 DRAM 이 20% 인 것은 **큰 배열을 전부 PSRAM 으로 뺐기 때문**이다. 처음에는
`dram0_0_seg overflowed by 469464 bytes` 로 링크가 깨졌다. 범인 셋:

- `csi_front.c` 의 `static float la[512×128]` = 262KB
- 스케치의 `wiq[512×2×128]`, `packed[512×2×128]` = 각 131KB

고친 방법 두 가지를 같이 썼다.

1. **`CF_MAX_IN` 을 512 → 128.** 2초 창에 실측 프레임률 10~22Hz 면 20~45프레임이다.
   512는 애초에 근거 없는 수였다. 실제로 들어온 창은 **19 프레임**이었다.
2. **`cf_window()` 이 스크래치를 인자로 받게 했다.** 함수 안 `static` 대형 배열은
   호출자가 배치를 못 고른다. 이제 호출자가 PSRAM 에 잡아 넘긴다.

같은 실수를 `synth_node` 에서 이미 한 번 했다(재생 버퍼 416KB). 규칙으로 적어둔다:
**수십 KB 를 넘는 배열은 `static` 으로 두지 말고 `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`.**
단 I2S DMA 버퍼만은 예외로 `MALLOC_CAP_DMA` — `MALLOC_CAP_INTERNAL` 은 IRAM 을 줄 수
있고 IRAM 은 16비트 접근이 불법이다(`LoadStoreError`).

리팩터가 수치를 안 건드렸는지 다시 대조했다: 파이썬 대비 **최대오차 1.371e-06**,
리팩터 전과 같은 값이다.

## 온보드 추론

`cn_infer.c` + `csi_front.c` 를 스케치에 넣어서 PSRAM 링(512프레임)에서 현재 채널의
프레임만 뽑아 시간순으로 정렬하고, 2초 창 → 인코더 → 프로토타입 코사인 매칭까지
보드에서 돈다. 프레임을 채널별로 거르는 이유는 채널이 섞이면 주파수 응답이 섞여
창이 무의미해지기 때문이다.

**다만 지금 실린 모델은 "채널 분류기" 다.** 사람 위치 라벨이 없어서 채널을 라벨로
써서 학습했다(`model/CSI_COLLECT.md`). 파이프라인이 끝단까지 도는지 검증하는 용도이지,
"어디에 사람이 있는가" 를 답하지는 않는다. 위치 라벨을 모으면 같은 코드로 바뀐다.

## 아직 안 한 것

- **보드에 못 구웠다.** 이 글을 쓰는 시점에 보드가 물리적으로 빠져 있다
  (`/dev/ttyUSB0` 없음, `lsusb` 에 CP2102 없음). 링크·수치 검증까지가 확인된 범위이고,
  LED 후보 4핀·PSRAM 링·온보드 추론 지연은 **실기 미검증**이다.
- **실제 움직임으로 검증하지 않았다.** 위 숫자는 전부 빈 방 기준선이다. K1 마크 기능이
  그걸 확인하기 위한 장치인데, 아직 아무도 안 눌렀다.
- **CSI 위치 라벨 미수집.** 사람이 5분 걸어다니며 버튼을 눌러줘야 한다.
- **BLE 기기 상한 48개.** 실측 39개로 여유가 있지만 붐비는 곳에서는 늘려야 한다.
- **CSI 프레임률 10~22Hz.** 능동 프로빙을 넣으면 ~180Hz 까지 올릴 수 있다(조사 확인).
  지금은 남의 트래픽만 받는 완전 수동이라 AP 가 조용하면 창이 안 찬다.
