# ESL 전자종이 화면 — 이 보드에 없는 화면을 밖에서 구한다

ESP32-Audio-Kit 에는 화면이 없다. 그래서 이 저장소의 모든 결과 — CSI 채널 일치율,
추론 지연, 대역 점수 — 가 시리얼로만 나왔고, 그건 PC 가 붙어 있어야 읽을 수 있다는
뜻이었다. Gicisky/PICKSMART BLE 전자선반라벨이 그 구멍을 메운다.

실기에서 **4대**가 잡힌다. 전부 `EPD 2.9" BWR`(id `0x0033`), 펌웨어 `0x8101`, 2.7~2.8V.

```
FF:FF:92:95:75:78  NEMR92957578
FF:FF:92:95:73:04  NEMR92957304
FF:FF:92:95:73:06  NEMR92957306
FF:FF:92:95:95:81  NEMR92959581
```

## 프로토콜

정본은 atc1441 의 리버스엔지니어링(`ATC_GICISKY_ESL`)과 그것을 이어받은
`eigger/hass-gicisky` 다.

```
서비스 0xFEF0   CMD 0xFEF1 (쓰기 + 알림)   IMG 0xFEF2 (쓰기)

1) CMD ← 01                        → 태그가 01 F4 00 (파트메시지 244) 로 답한다
2) CMD ← 02 [총길이 LE32] 00 00 00
3) CMD ← 03                        → 시작
4) IMG ← [파트번호 LE32][데이터 240B]
5) 태그가 05 [상태] [다음파트 LE32] 로 다음 것을 요구한다. 상태 08 이면 완료.
```

픽셀은 **열 우선**이다. 열 하나가 16바이트(128비트), 296열이므로 평면당 4736바이트.
BW 평면은 `1=흰색`, RED 평면은 **반전되어** `1=적색 없음`이다. 적색 평면을 0 으로
채웠더니 화면 전체가 빨개지고 글자만 희게 나왔다(실기 관측).

## 참조 구현과 다르게 만든 것

### 1. MAC 을 박지 않는다 — 광고에서 모델을 읽는다

태그는 광고에 **제조사 데이터(회사 ID `0x5053`, 5바이트)** 를 싣는다. **연결하지 않고**
모델·배터리전압·펌웨어를 알 수 있다.

```
device_id = ((d[4] << 8) | d[0]) & 0x3FFF
battery   = d[1] / 10          (볼트)
firmware  = (d[2] << 8) | d[3]
```

이게 중요한 이유는 **같은 296x128 이 다섯 변종**이기 때문이다.

| id | 모델 | 적색 |
|----|------|------|
| 0x0028 | EPD 2.9" BW | 없음 |
| 0x0030 | EPD 2.9" BW_1 | 없음 |
| 0x002B | EPD 2.9" BWR | 있음 |
| 0x0033 | EPD 2.9" BWR | 있음 |
| 0x002E | EPD 2.9" BWRY | 4색 |

BW 모델에 두 평면(9472바이트)을 보내면 태그가 기대량의 두 배를 받는다. 증상은
"화면이 나오긴 하는데 완벽하지 않다" 로만 보여 원인이 감춰진다. 모델 표
(`esl_bwr.cpp`의 `MODELS[]`)는 `hass-gicisky` 의 `devices.py` 에서 옮겼고,
11개 모델(2.1"~10.2")을 담고 있다. **다른 이잉크를 가져다 꽂아도 코드를 안 고친다.**

### 2. 실패 사유를 열거형으로 돌려준다

참조 구현은 `bool` 이라 어디서 죽었는지 모른다. 연결 실패인지, 0xFEF0 이 없는
기기인지, 구독이 안 걸린 것인지 구분되어야 고칠 수 있다.

### 3. 전송 시간을 잰다

"느리다" 를 고치려면 숫자가 먼저 있어야 한다. 실측 40파트 / 3.1~5.7초 / 2.2~2.9 KB/s.

## 실기에서 배운 것

### `delete cli` 하면 죽는다

전송마다 `createClient`/`delete` 를 했더니 매번 이 자리에서 죽었다.

```
assert failed: xQueueGenericSend queue.c:937
BLEClient::gattClientEventHandler → ESP_GATTC_DISCONNECT_EVT
  → m_semaphoreOpenEvt.give(ESP_GATT_IF_NONE)      (BLEClient.cpp:535)
```

끊김 이벤트가 `delete` **뒤에** 도착해서 해제된 객체의 세마포어를 건드린다.
Bluedroid 가 클라이언트 포인터를 계속 들고 있으므로 우리가 먼저 지우면 안 된다.
**클라이언트를 하나만 만들어 재사용하고 삭제하지 않는다.** 객체 하나가 새지만
네 대를 돌려 쓰는 데 문제가 없다.

### `subscribe()` 는 NimBLE 전용이다

`BLERemoteCharacteristic::subscribe()` 가 헤더에 있지만 **NimBLE 백엔드 선언부**에
있어서 Bluedroid 빌드에서는 존재하지 않는다(컴파일 에러로 확인). Bluedroid 경로는
`registerForNotify()` + CCCD(0x2902) 직접 쓰기뿐이다. 쓴 뒤 되읽어 `01 00` 을
확인한다 — 구독이 조용히 실패하면 증상이 "협상 무응답" 하나로만 보인다.

### 부팅 후 첫 전송은 파트 크기를 20 으로 협상한다

같은 태그가 두 번째 회차에서는 244 를 준다. 20 이면 파트가 592개가 되어 21초가
걸리고, 244 면 40개로 3.5초다. **5배 차이인데 태그 특성이 아니라 세션 특성이다.**
한 번 다시 물어보게 했지만 같은 연결 안에서는 값이 안 바뀐다 — 재연결이 필요하다.

### 적색을 빼도 빨라지지 않는다

이론상 페이로드가 절반(9472→4736바이트, 40→20파트)이니 절반쯤 빨라져야 한다.
같은 환경에서 회차마다 번갈아 재봤다.

| | 바이트 | 파트 | 평균 |
|---|---|---|---|
| 흑백+적색 | 9472 | 40 | **4074ms** (11회) |
| 흑백만 | 4736 | 20 | **4327ms** (8회) |

**차이가 없다(0.94배).** 병목이 BLE 바이트가 아니라 연결 수립과 태그 자신의
전자종이 리프레시다 — 그건 내용량과 무관하게 몇 초 걸린다. 그러므로 적색을 쓸지는
**속도 문제가 아니라 가독성 선택**이다.

### 참조 웹 업로더의 버그

`atc1441.github.io/ATC_GICISKY_Paper_Image_Upload.html` 의 압축 경로에서 적색 평면이
`byteDataRed` 가 아니라 `byteData` 를 계속 읽는다(`currentPosi` 가 BW 배열 끝을
넘어간다). 압축 + 2색을 같이 켜면 적색 평면에 흑백 데이터가 실린다.

## 적색을 어디에 쓸 것인가

전자종이에서 적색의 유일한 장점은 **읽지 않아도 눈에 들어온다**는 것이다. 방
건너편에서 곁눈으로도 보인다. 숫자·그래프·라벨은 가까이서 읽으므로 검정이 더
선명하다. 그러니 적색을 쓸 값이 있는 것은 **"안 봐도 알아야 하는 이진 상태" 하나**뿐이다.

그런데 지금 그 알람(대역 점수 임계 초과)은 **실제 움직임으로 검증된 적이 없다.**
검증 안 된 감지기에 적색을 걸면 노이즈에도 빨개지고, 그러면 적색이 아무 의미가
없어진다. 그래서 **감지기가 스스로 자격을 증명해야** 적색이 켜지게 했다 —
K1 로 마크한 구간과 안 한 구간의 분리도(Cohen's d)가 0.8 을 넘을 때만.

## 아직 안 한 것

- **압축 미지원.** 3.7"·7.5"·10.2" 모델은 압축 포맷을 쓴다. 표에는 플래그만 있고
  인코더가 없으므로 그 모델을 물리면 화면이 깨진다.
- **BWRY(4색) 미지원.** 렌더러가 두 평면만 만든다.
- **회전·좌우반전을 표에서 안 읽는다.** 지금은 296x128 / mirror_x 로 고정돼 있어
  다른 크기 모델을 물리면 어긋난다.
- **`73:04` 는 BWR 로 광고하는데 적색이 안 나온다.** 처음엔 BW 모델이라 페이로드
  길이가 틀린 것으로 봤는데, 광고를 읽어보니 다른 세 대와 같은 `0x0033` 이었다.
  그 태그 개체의 문제로 보이지만 확인하지 못했다.
