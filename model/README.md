# 캐빈 노드 — ESP32 온디바이스 음성 인식 모델

ESP32-Audio-Kit 이 사람 말을 알아듣게 만드는 초소형 모델. 학습은 3090 에서 1회,
런타임은 ESP32 단독 (PC 없음, 클라우드 API 없음, SD 카드 없음).

## 왜 이 구조인가

먼저 안 되는 것을 못 박아야 설계가 선다. **생성 모델은 4MB 플래시에 물리적으로
안 들어간다.** Supertonic 3 (TTS) 는 ONNX 총 398MB 고, int8 로 눌러도 100MB 급이다.
Whisper tiny 도 39M 파라미터다. TTS·STT·LLM 은 이 칩에서 두 자릿수 배율로 부족하다.

그런데 차 안 음성의 실제 효용 대부분은 자유 작문이 아니라 **의도 파악**이다.
그래서 이렇게 나눴다:

| 역할 | 어디서 | 무엇 |
| --- | --- | --- |
| 학습 데이터 합성 | PC (1회성) | Supertonic 3 — 한국어 발화 4,525개, 사람 녹음 0회 |
| **인식 (런타임)** | **ESP32** | 이 저장소의 인코더, 69.4K 파라미터 |
| 응답 음성 | 태블릿 또는 플래시 | 태블릿이 즉석 합성 → WiFi → PSRAM 캐시 / 또는 플래시의 ADPCM |

## 핵심 설계: 분류기가 아니라 임베딩

라벨을 **인텐트(27개)가 아니라 문장(93개)** 으로 두고 metric learning 을 한다.
인식은 마이크 임베딩과 등록된 문장 임베딩의 코사인 최댓값을 고르는 것뿐이다.

이유는 하나다. **새 명령 추가에 재학습이 필요 없어야 한다.** 인텐트 분류기로
학습하면 28번째 명령을 넣으려면 다시 학습해야 한다. 문장 단위로 "같은 말은 같은
벡터" 를 배우면, 새 문장은 임베딩 평균 한 번으로 등록된다 — ESP32 는 학습을 못 하지만
평균은 낸다.

그게 진짜 되는지 측정했다: 문장 27개를 학습에서 **완전히 제외**하고, 등록만으로
맞히는지 봤다.

## 측정 결과

RTX 3090, 120 에폭 3분. 보류 보이스 F5/M5 는 학습에 일절 쓰지 않았다.

| 지표 | 값 |
| --- | --- |
| 파라미터 | **69.4K** (float32 268KB) |
| 추론 1회 | **8.14M MAC** |
| 문장 정확도 — 학습된 문장, 처음 듣는 목소리 | **0.942** |
| **문장 정확도 — 학습에서 제외한 문장** | **0.963** ← 재학습 없이 명령 추가가 되는지의 지표 |
| 인텐트 정확도 (86 프로토타입 → 27 인텐트) | **0.948** (489/516) |
| OOD 오수락 (명령 재현율 95% 기준) | **8.1%** (222클립) ← 예전 방식 66.2% |

오수락 8.1% 은 약한 문구 7개를 프로토타입에서 뺀 뒤의 값이다. 그 7개는 이 평가셋으로
골랐으므로 낙관적이고, **교차검증 추정은 15.8% → 10.1%** 다 (아래 "약한 문구" 절).

`model/out/train_perphrase2.log`, `model/out/enroll_report.json`,
`model/out/reject_eval2.json` 에 원본이 있다.

### 도중에 틀렸던 것 두 개

기록해 둘 가치가 있어서 남긴다.

**1. 인텐트당 프로토타입 1개는 실패한다 (0.667).** 한 인텐트의 서로 다른 문장
("에어컨 켜줘" / "시원하게 해줘" / "냉방 켜줘") 을 평균했는데, 인코더는 애초에 다른
문장을 **멀리 떼어놓도록** 학습됐다. 그 평균은 어느 문장에도 가깝지 않은 헛점이 된다.
학습 목표와 등록 방식이 서로 싸운 것이다. 문장당 1개로 바꾸니 0.667 → **0.893**.

**2. 점수 정규화로 OOD 를 잡으려던 시도는 실패했다.** "도메인 내 발화는 자기
프로토타입만 튀고 OOD 는 고르게 닮을 것" 이라 보고 `top1-top2`, `top1-mean` 을
시험했다. 결과는 개선 없음(52.8% 동일) 또는 악화(91.7%). 가설이 틀렸다.

## OOD 거부 — 66.2% → 8.1% (교차검증 10.1%)

한동안 "명령이 아닌 말을 절반 넘게 명령으로 받는다" 가 이 모델의 미해결 문제였다.
원인은 학습 설계였다. `train.py` 가 OOD 클립을 학습 라벨에서 제외했으므로 인코더는
"학습 문장을 서로 떼어놓는 법" 만 배웠다. 처음 듣는 문장은 아무 데나 떨어지고,
프로토타입이 93개면 그중 하나와는 우연히 가깝다.

**고친 방법: OOD 를 학습 라벨에 넣는다. 단, 인텐트가 아니라 문장 단위로.**
`--ood-mode perphrase` 가 기본값이다. 이 프로젝트의 규칙("라벨은 문장")을 OOD 에도
그대로 적용한 것이고, 그 결과 인코더는 명령 아닌 말을 명령에서 능동적으로 밀어낸다.
OOD 문장은 30개 → 311개로 늘렸다(`ood_texts.json`). 개수보다 중요한 건 구성인데,
명령과 어휘를 공유하는 **하드 네거티브**("에어컨 소리가 좀 크네", "집에서 회사까지
얼마나 걸려")가 원래 하나도 없었다.

같은 데이터·같은 평가셋(보류 보이스 F5/M5, 학습에 안 쓴 OOD 문장 222클립),
명령 재현율 95% 지점:

| 학습 방식 | OOD 오수락 | AUROC | 인텐트 정확도 |
| --- | --- | --- | --- |
| `exclude` (예전 동작) | 66.2% | 0.889 | 0.928 |
| `single` (OOD 전부 한 클래스) | 46.2%\* | 0.912 | — |
| **`perphrase` (현재)** | **15.8%** | **0.970** | **0.944** |

\* 1차 데이터셋에서 측정. 명확히 지므로 2차에서는 돌리지 않았다.

거부가 좋아졌는데 인식 정확도도 같이 올랐다(0.928 → 0.944). 거부를 위해 정확도를
내준 게 아니다 — "여기는 명령이 아니다" 라는 경계가 생기면 명령끼리도 더 잘 갈린다.

### 이 과정에서 반박된 것

**1. "OOD 전부를 한 클래스로 묶는다" 는 더 나쁘다(46.2%).** 서로 무관한 문장을 한
점에 모으라는 목표가 인코더와 싸운다. 인텐트당 프로토타입 1개가 실패한 것과 같은
이유다.

**2. "OOD 프로토타입 은행" 은 기대만큼 안 남는다.** 명령 프로토타입 외에 OOD
프로토타입까지 두고 (명령 최고 코사인 − OOD 최고 코사인) 으로 자르는 기제다.
1차 데이터셋에서는 극적으로 보였다(`exclude` 33.9% → 3.8%) — 채택 직전까지 갔다.
그런데 짧은 추임새를 평가셋에 충분히 넣으니 이득이 거의 사라졌다
(`perphrase` 15.8% → 13.1%, 플래시 109KB, 앱 여유 290KB 중 3분의 1).
**1차 결론은 평가셋이 쉬웠던 탓이었다.** 기제는 코드에 남기되 기본은 끈다
(`enroll.py --ood-bank`). 펌웨어는 마진 판정식 하나로 통일했고, 은행이 비면
예전 절대 임계값 판정으로 그대로 축퇴한다.

**3. 예전의 52.8% 자체가 신뢰할 수 없는 수였다.** OOD 평가가 36클립(고유 문장 6개)
위에 있었고 — 보이스 배정이 `(vi*6+k)%30` 순환이라 F5/M5 에 걸린 OOD 문장이 6개뿐
이었다 — 재학습만 해도 44%~72% 를 오갔다. 지금은 222클립이고, 문장마다 보류 보이스를
반드시 합성해 둔다.

### 약한 문구를 프로토타입에서 뺀다 — 15.8% → 10.1%

남은 오수락이 `short` 그룹에 몰려 있었다(42.6%). 처음엔 **발화 길이**를 판정에 넣으려
했는데, 재보니 못 쓴다:

- 가장 짧은 명령 11개가 **전부 정확히 1.30초**다(합성기가 최소 길이로 채운다).
  OOD `short` 그룹은 중위 1.36초 — 길이 분포가 거의 겹친다.
- 짧은 입력만 떼어 보면 AUROC 0.893(긴 입력 0.980)이고, 짧은 구간에서 재현율 95% 를
  맞추려면 임계값을 **내려야** 한다(0.590 대 전역 0.601). 짧은 명령의 점수가 더 낮기
  때문이다. 그래서 구간별 임계값은 오수락을 오히려 올린다(55.6% 대 48.1%).
- 게다가 `short` OOD 의 절반은 1.35초보다 길다. 길이 문제가 아니었다.

문제는 짧은 **명령 문구** 쪽이었다. 오수락된 OOD 가 걸리는 프로토타입은 전부
1.28~1.46초짜리다("정지", "다음 곡", "더 크게", "아니야"). 그러면 고칠 곳은 모델이 아니라
명령 사전이다 — 그게 이 설계에서 가장 값싼 개선이다.

고르는 방법이 중요하다. 평가셋에 대고 탐욕적으로 솎으면 그 평가셋에 과적합된다. 그래서
OOD 평가셋을 절반으로 갈라 **한쪽에서 솎고 다른 쪽에서 재는 것**을 6시드 양방향 12회
반복하고, 8/12 이상 합의된 문구만 남겼다.

```
홀드아웃 기준 (12회 분할 평균)
  오수락      전체 문구 15.77%  →  솎아낸 뒤 10.06%   (12/12 분할 전부 개선)
  인텐트      0.9444           →  0.9475            (대가 없음, 오히려 소폭 상승)
```

합의된 7개: `온도 낮춰` `다음 곡` `좀 시원하게` `더 크게` `감사합니다` `조용히` `정지`.
`commands.json` 의 `weak_phrases` 에 적혀 있고, `enroll.py --no-weak-filter` 로 끄고
비교할 수 있다. 인텐트마다 더 긴 대체 문구가 최소 2개 남는다.

**학습 데이터에서는 빼지 않는다.** 인코더는 문장 단위로 학습되므로 이 문장들도 클래스로
남아 있는 것이 임베딩 공간에 이롭다. 빼는 것은 보드가 매칭하는 대상(`prototypes.h`)뿐이다.
평가에서도 그 문구의 클립을 뺀다 — 제품에서 사라진 문구를 계속 채점하면 사용자가 말할 수
없는 문구로 감점되는 셈이다.

전체 평가셋에 적용한 결과(위 표의 8.1%)는 문구를 이 셋으로 골랐으므로 낙관적이다.
믿을 숫자는 교차검증 쪽 10.1% 다. 그룹별로는 `short` 42.6% → 22.2%,
`chitchat` 12.9% → 5.7%, `hard_negative` 3.2% → 1.6%.

**대가 하나는 사용자 쪽에 있다**: `감사합니다` 는 가장 정중한 형태다. 고마워/고맙다/잘했어가
남지만 이건 제품 판단이므로, 되돌리려면 `weak_phrases` 에서 한 줄 빼면 된다.

### 남은 약점 — 짧은 추임새

약한 문구를 뺀 뒤에도 오수락의 대부분이 한 그룹에서 나온다:

| OOD 그룹 | 오수락 | n |
| --- | --- | --- |
| baseline30 (최초 30문장) | 2.8% | 36 |
| hard_negative (명령 어휘 공유) | 1.6% (제외 전 3.2%) | 62 |
| chitchat (일상 발화) | 5.7% (제외 전 12.9%) | 70 |
| **short (짧은 추임새)** | **22.2%** (약한 문구 제외 전 42.6%) | 54 |

짧은 명령("정지", "취소", "그만", "야", "넘겨")과 짧은 추임새("그럼", "역시", "가자")는
길이도 음소 수도 비슷해서 실패가 여기 몰린다. `short` 그룹에는 "가자", "어디야" 처럼
사람도 헷갈릴 발화를 일부러 넣었으니 이 값은 상한에 가깝다 — 그 그룹을 빼면 3.6% 다.
그래도 다음 개선 지점은 여기다:

1. 호출어 게이트를 앞에 둔다 (상시 인식 자체를 피하는 실전 완화책)
2. 남은 짧은 명령("야", "취소", "됐어", "그만", "넘겨", "잠금")에 접두어를 붙여 길이를
   벌린다 — 문구 변경은 재학습이 필요 없다
3. ~~발화 길이를 판정에 넣는다~~ — 재봤고 **안 된다**(위 "약한 문구" 절). 짧은 명령과
   짧은 추임새의 길이 분포가 겹치고, 구간별 임계값은 오수락을 오히려 올린다.

## 파이프라인

```
commands.json                       27 인텐트 · 93 문장 · 응답 · 톤 프리셋
ood_texts.json                      명령 아닌 말 311 문장 (하드 네거티브 포함)
   ↓  gen_data.py                   Supertonic 3 으로 합성 (10 보이스 × 3 속도)
model/data/utterances/              4,525 클립 / 음성 125분 / 33분 소요 (RTF 0.26)
   ↓  train.py                      metric learning, 잔향·노이즈·마스킹 증강
model/out/encoder.pt                69.4K 파라미터
   ↓  enroll.py                     문장별 프로토타입 → prototypes.h
   ↓  export.py                     BN 폴딩 → model_data.h / model_weights.h / selftest.h
firmware/cabin_node/                ESP32 가 그대로 컴파일
```

### 재현

```bash
# 1) Supertonic 3 모델 (약 396MB)
pip install --break-system-packages supertonic
hf download Supertone/supertonic-3 --local-dir ~/supertonic-3-assets

# 2) 데이터 합성 (명령 20분 + OOD 13분)
python3 model/scripts/gen_data.py --assets ~/supertonic-3-assets

# 2b) OOD 만 늘릴 때는 증분으로 (ood_texts.json 에 문장 추가 후)
python3 model/scripts/gen_data.py --ood-only --assets ~/supertonic-3-assets

# 3) 학습 (3090 에서 약 3분)
cd model/scripts && python3 train.py --epochs 120 --bs 64

# 4) 등록 + 내보내기
python3 enroll.py && python3 export.py

# 4b) 거부 기제를 바꿀 때 — 재현율을 고정해 놓고 오수락을 비교한다
python3 eval_reject.py --ckpt ../out/encoder.pt \
  --ood-trained-from ../out/encoder.pt --data ../data/utterances

# 5) C 추론이 파이썬과 같은 값을 내는지 검증
cd ../.. && gcc -O2 -std=c99 -Ifirmware/cabin_node \
  model/scripts/parity_test.c firmware/cabin_node/cn_infer.c -lm -o /tmp/parity
/tmp/parity model/out/encoder.bin
```

## 수치 검증 — 보드에 올리기 전에 통과해야 하는 것

임베디드 추론에서 가장 흔한 실패는 "돌긴 도는데 값이 미묘하게 다름" 이고, 그건 데모
중에 **정확도 문제로 위장해서** 나타난다. 그래서 세 단계로 막았다.

| 단계 | 무엇을 비교 | 측정된 오차 |
| --- | --- | --- |
| BN 폴딩 | torch 원본 ↔ numpy 참조 구현 | 최대 1.49e-07 |
| C 이식 | numpy 참조 ↔ gcc 로 컴파일한 `cn_infer.c` | 임베딩 코사인 0.9999999 |
| 보드 자기검증 | 알려진 멜 입력 ↔ 알려진 임베딩 (`selftest.h`) | 부팅 시 자동, 허용 2e-3 |

`cn_infer.c` 가 ESP-IDF 에 의존하지 않는 순수 C99 인 이유가 이것이다 — 같은 파일을
gcc 로 컴파일해 PC 에서 검증할 수 있다.

## 왜 int8 이 아니라 float32 인가

ESP32 는 단정밀도 FPU 가 있고 **SIMD 가 없다.** int8 로 내려도 dot-product 명령이
없어서 속도 이득이 거의 없고, 양자화 오차만 생긴다. 메모리는 PSRAM 4MB 로 넉넉하다
(가중치 268KB + 활성값 약 490KB). 그래서 학습과 추론이 수치적으로 같아지는 float32 를
택했다. 속도가 부족해지면 그때 int8 을 얹는 것이 순서다.

## 미확인 항목

- **보드 핀 배치** (`firmware/cabin_node/board_pins.h`) — 실크스크린을 읽지 않고
  소프트웨어로만 식별했다. AC101 I2C 프로브로 런타임에 검증하게 해 뒀지만, 실물
  확인 전에는 가정이다.
- **온보드 실측 추론 시간** — 8.14M MAC 에서 200~400ms 로 추정하지만 측정하지 않았다.
  보드에 굽지 않았다 (공장 펌웨어가 아직 살아 있고, 덮어쓰기 전에 확인이 필요하다).
- **실제 마이크 인식률** — 위 숫자는 전부 합성 음성 기준이다. 잔향·노이즈 증강을
  넣었지만 실제 캐빈 마이크 성능은 별개다.
