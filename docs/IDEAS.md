# 뭘 할까 — 용도 판단

## 0. 전제: 이 보드의 유일한 강점

일반 ESP32 와의 차이는 **오디오 입출력 하나**다. BLE·ESP-NOW·WiFi·GPIO 는 어느 ESP32 나
하고, 이 보드는 오히려 코덱+SD+PSRAM 이 핀을 먹어 **남는 GPIO 가 더 적다.**

그래서 판단 기준이 단순하다: **소리를 안 쓰는 용도라면 이 보드를 고르는 게 손해다.**
릴레이 제어, 센서 확장, 디스플레이 노드 같은 건 맨 DevKit 이 더 낫다.

---

## 1. 차량에 어디 들어가나

먼저 정직하게: **이 개발보드 자체는 차량에 안 들어간다.** AEC-Q100 미인증, micro-USB
커넥터, 취미용 전원부, CAN 트랜시버 없음, 방진방수 없음. 벤치 프로토타입이다.

들어가는 건 이 보드가 *대신하는 기능 블록*이다. 그 기능이 실차에서 어디에 있는지:

### 1.1 AVAS — 저소음자동차 경고음발생장치 ★ 가장 잘 맞는 자리

전기차가 저속에서 조용해 보행자가 위험한 문제 때문에, 외부로 경고음을 내는 장치가
**법정 의무**다. 관련 기준은 UN R138, 미국 FMVSS 141, 국내는 자동차 안전기준의 저소음
자동차 경고음발생장치 조항이다. (구체적 조항 번호·발효일·음압 기준값은 이 문서에서
확정하지 않았다 — 설계 전에 원문 확인 필요.)

**왜 이 보드가 프로토타입으로 딱 맞나** — 블록도가 실제 AVAS ECU 와 같다:

| AVAS ECU 블록 | 이 보드의 대응 |
| --- | --- |
| 차속·기어 입력 (CAN) | 외부 CAN 트랜시버 모듈 필요 (칩의 TWAI 사용) |
| 속도 연동 음 합성 | ESP32 듀얼코어 + 4MB PSRAM |
| D/A + 파워앰프 | AC101 코덱 + 온보드 앰프 |
| 외부 스피커 (프론트 범퍼/엔진룸) | 스피커 출력 단자 |

실차 위치는 **프론트 범퍼 안쪽 또는 엔진룸 전방**, 스피커가 바깥을 향한다.
속도에 따라 주파수·음량이 변하고, 일정 속도(보통 20km/h 대) 이상에서 꺼진다.

**이게 가장 좋은 답인 이유:** 법으로 필요한 실제 장치이고, 필요한 부품이 이 보드에 이미
다 있고, 만들면 "동작하는 데모"가 나온다. 나머지 후보는 전부 이보다 약하다.

### 1.2 경고음 / 차임 모듈

안전벨트 미착용, 도어 열림, ADAS 제어권 이양 경고 같은 실내 경고음. 실차에서는 보통
**클러스터 내부** 또는 IP(인스트루먼트 패널) 뒤의 전용 차임 모듈에 있고, BCM 이 트리거한다.

이 보드로는 소리 품질을 훨씬 올릴 수 있다 — 부저 톤이 아니라 실제 샘플·음성을 재생한다.
PLEOS 재구성 데모에 붙이면 링크 결함/재구성을 음성으로 알릴 수 있다 (아래 2.2).

### 1.3 캐빈 음성 HMI 마이크 노드

음성 인식용 원거리(far-field) 마이크. 실차 위치는 **오버헤드 콘솔 또는 헤드라이너**
(운전자 입 방향), 2열 대응 시 B/C필러나 후석 천장에 추가.

이 보드에 마이크가 2개 있어서 2채널 빔포밍 프로토타입까지는 된다. 다만 실차용 마이크
어레이는 보통 4~6채널이라, 개념 검증 수준이다.

### 1.4 실내 음향 이벤트 감지

후석 승객(아이 울음) 감지, 유리 파손 감지, 이상 소음 진단. 실차에서는 OMS/DMS 모듈에
통합되거나 전용 센서로 들어간다. 마이크만 있으면 되니 이 보드로 프로토타입 가능.

### 1.5 안 되는 것 — 명확히

- **ANC (능동 소음 제어)**: 로드 노이즈 상쇄는 마이크→연산→스피커 루프가 마이크로초
  단위여야 한다. ESP32 로는 못 한다. 전용 오디오 DSP 영역.
- **TSN / 이더넷 오디오 엔드포인트**: 이 보드에 이더넷 PHY 가 없다.
  다만 **LAN9662 와 조합**하면 의미가 생긴다 — LAN9662 가 TSN(AVB, IEEE 1722 AVTP)으로
  오디오 스트림을 나르고, ESP32 가 그걸 소리로 낸다. KETI 의 TSN 작업과 직접 연결되는
  유일한 조합이다. 단 ESP32 가 네트워크에 직접 못 붙으니 PC 나 보드가 브리지 역할을
  해야 하고, 그 구간이 실차 구조와 달라진다 — 데모용으로만 정직하다.

## 2. 태블릿과 뭘 같이 할까

### 2.1 재플래시 0줄 — 오늘 바로 되는 것 ★ 먼저 이걸 해볼 것

태블릿이 이 보드를 **A2DP 블루투스 스피커로 페어링**하면, 태블릿 앱의 TTS·경보·알림음이
실제 캐빈 스피커로 나온다. 공장 펌웨어 그대로, 코드 한 줄 안 쓰고 된다.

ROii / PLEOS 태블릿 앱들은 이미 Android 라 시스템 TTS 가 있다. "화면만 있고 소리가 없던"
데모에 소리가 붙는다. 투자 대비 효과가 압도적으로 좋고, 실패해도 잃는 게 없다.

한계: 태블릿→보드 단방향이고, 어떤 소리를 낼지는 태블릿이 정한다. 보드는 그냥 스피커다.

### 2.2 BLE 이벤트 → 소리 (재플래시 필요)

태블릿이 BLE 로 이벤트를 보내고 보드가 해당 음성/경보음을 재생. PLEOS 재구성 데모의
BLE 체인 패턴을 그대로 재사용하면 된다 (`pleos/hardware/esp32_reconfig` 의 컨트롤러↔노드
구조). "Path 1 링크 상실, 재구성" 같은 음성이 나온다.

2.1 보다 나은 점 — 소리 결정 로직이 보드에 있어서 태블릿이 죽어도 경보가 난다.
페일세이프 관점에서 이게 실차에 가깝다.

### 2.3 보드 = 마이크, 태블릿 = 두뇌

보드가 캐빈 마이크로 음성을 받아 WiFi 로 태블릿에 스트리밍, 태블릿이 STT·LLM·TTS 를
돌리고 결과 음성을 다시 보드로. 태블릿에 연산과 네트워크가 있으니 역할 분담이 맞다.

보드가 굳이 필요한 이유는 하나뿐이다: **태블릿 마이크보다 좋은 위치에 놓을 수 있다**
(천장, 후석). 태블릿 마이크로 충분한 상황이라면 이건 하지 말 것.

## 3. AI 기능 — 되는 것과 안 되는 것

### 3.1 온디바이스: 기대를 낮춰야 한다

**이 칩은 AI 추론 플랫폼이 아니다.** ESP32-D0WD 에는 벡터 명령이 없다. Espressif 의
음성 인식 프레임워크 ESP-SR 은 이 사실 때문에 신형 모델을 ESP32-S3 로 옮겼다:

| ESP-SR 기능 | ESP32(이 보드) | 비고 |
| --- | --- | --- |
| WakeNet (호출어 감지) | 구형 모델만, 지원 축소 | 신형 모델은 S3 요구 |
| MultiNet (명령어 인식) | **불가** | ESP32-S3 필요 |
| 한국어 | **미지원** | 중국어/영어만 |

(ESP-SR 의 지원 범위는 버전마다 바뀐다. 위 내용은 착수 전에 현재 ESP-SR 문서로 재확인할 것.)

여기에 **플래시 4MB** 라는 하드 제약이 겹친다. 호출어 모델 + 앱 + 파티션이 4MB 에 다
들어가야 해서, 공장 파티션 스킴(900K + 1536K + 1536K)을 재설계해야 한다.

**온디바이스로 현실적인 것:**

- VAD (음성 구간 검출) — 가볍고 확실히 된다
- 음압 레벨 / 간단한 스펙트럼 특징 추출
- 아주 작은 NN 분류기 (몇 가지 소리 구분 수준)
- 호출어 하나 정도 (영어, 구형 모델, 성능 기대치 낮게)

### 3.2 현실적 구조: 이 보드는 AI 의 오디오 프런트엔드

무거운 건 밖에서 돌리고, 보드는 마이크·스피커·VAD 만 맡는다. 이게 정직한 역할 분담이다.

```
[보드]  마이크 → VAD/호출어 → PCM(또는 Opus) 를 WiFi 로 스트리밍
                                        │
[호스트: PC / 태블릿 / 서버]            ▼
        STT  ──→  LLM  ──→  TTS  ──→  오디오를 보드로 되돌려 재생
```

**중요 — Anthropic API 는 STT/TTS 를 제공하지 않는다.** Claude 는 LLM 구간만 담당하고,
STT(로컬 Whisper 등)와 TTS 엔진은 별도로 붙여야 한다. 이걸 착각하면 설계가 어긋난다.

### 3.3 LLM 구간 — 모델 선택과 비용

| 모델 | 모델 ID | 컨텍스트 | 입력 $/MTok | 출력 $/MTok |
| --- | --- | --- | --- | --- |
| Claude Haiku 4.5 | `claude-haiku-4-5` | 200K | $1 | $5 |
| Claude Sonnet 5 | `claude-sonnet-5` | 1M | $3 (도입가 $2, 2026-08-31 까지) | $15 (도입가 $10) |
| Claude Opus 5 | `claude-opus-5` | 1M | $5 | $25 |

**차량 음성 어시스턴트에는 `claude-haiku-4-5` 로 시작하는 게 맞다.** 응답 지연이 체감
품질을 지배하는 구간이라, 추론 능력보다 속도·비용이 중요하다. 명령 해석과 짧은 응답
생성은 Haiku 로 충분하다. 복잡한 상황 판단이 필요한 질의만 `claude-sonnet-5` 로 보내는
2단 구성이 실용적이다.

**주의할 점 두 가지:**

1. **응답을 스트리밍으로 받아 첫 문장부터 TTS 를 시작해야 한다.** 전체 응답을 기다리면
   지연이 그대로 사용자에게 노출된다. 음성 어시스턴트에서 이게 가장 큰 체감 개선이다.
2. **프롬프트 캐싱 최소 길이가 모델마다 다르다.** `claude-haiku-4-5` 는 4096 토큰 미만이면
   캐싱이 아예 안 걸린다(에러 없이 조용히 무시된다). 짧은 시스템 프롬프트라면 Haiku 에서는
   캐싱 이득을 기대하지 말 것. `claude-sonnet-5` 는 1024, `claude-opus-5` 는 512 토큰.

LLM 구간 최소 예시 — 문장 단위로 잘라 TTS 로 넘기는 형태:

```python
import anthropic

client = anthropic.Anthropic()

SYSTEM = (
    "너는 차량 내 음성 어시스턴트다. 운전 중에 듣는 답변이므로 "
    "한두 문장으로 짧게, 목록이나 기호 없이 말하듯 답한다."
)

SENTENCE_END = ".?!"

def answer(transcript: str, speak):
    """transcript: STT 결과. speak: 문장 하나를 TTS 로 재생하는 콜백."""
    buf = ""
    with client.messages.stream(
        model="claude-haiku-4-5",
        max_tokens=512,              # 짧은 음성 응답이므로 의도적으로 작게
        system=SYSTEM,
        messages=[{"role": "user", "content": transcript}],
    ) as stream:
        for chunk in stream.text_stream:
            buf += chunk
            # 문장이 끝나는 대로 TTS 로 넘겨 첫 소리까지의 지연을 줄인다
            while True:
                cut = next(
                    (i for i, ch in enumerate(buf) if ch in SENTENCE_END), -1
                )
                if cut < 0:
                    break
                sentence, buf = buf[: cut + 1].strip(), buf[cut + 1 :]
                if sentence:
                    speak(sentence)
        if buf.strip():
            speak(buf.strip())
```

`claude-haiku-4-5` 는 구세대 모델이라 `thinking` 을 생략하면 사고 과정 없이 바로 답한다 —
음성 루프에는 이게 맞다. `claude-sonnet-5` 로 올릴 때는 적응형 사고가 기본 켜짐이므로,
지연이 중요하면 `thinking={"type": "disabled"}` 를 명시해야 한다.

## 4. 정리 — 추천 순서

| 순위 | 할 일 | 재플래시 | 근거 |
| --- | --- | --- | --- |
| 1 | 태블릿을 A2DP 로 페어링해 태블릿 TTS 를 캐빈 스피커로 출력 | **불필요** | 0분, 실패 위험 0, 데모에 바로 보탬 |
| 2 | PLEOS 재구성 데모용 음성 경보 노드 (BLE 이벤트 → 음성) | 필요 | 기존 BLE 체인 재사용, 다른 보드가 못 하는 역할 |
| 3 | AVAS 프로토타입 (속도 연동 경고음) | 필요 | 법정 장치, 블록도가 실제 ECU 와 동일 |
| 4 | 오디오 프런트엔드 + 외부 STT/LLM/TTS 음성 어시스턴트 | 필요 | 구조는 명확하나 STT/TTS 선정 등 작업량 큼 |
| — | Path 3 노드로 전용 | 필요 | **비추천** — 이 보드의 강점을 하나도 안 쓴다. 맨 DevKit 이 낫다 |
| — | TSN / 이더넷 관련 | — | **불가** — PHY 없음 |
| — | ANC | — | **불가** — 루프 지연이 자릿수로 부족 |
